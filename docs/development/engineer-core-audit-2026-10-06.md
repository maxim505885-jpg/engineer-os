# ENGINEER CORE — проверка состояния 06.10.2026

Цель — проверить существующее инженерное ядро и укрепить подтверждённые слабые
места, сохраняя бесплатный локальный маршрут, ТЗ как управляющий объём проверки,
Evidence before conclusion и fail-closed принятие. Windows проверяется последним.
Эта проверка кода не является FINAL AUDIT инженерного объекта.

## Фактическое состояние

| Часть | Что реализовано | Что ещё требуется |
|---|---|---|
| EngineerCore | Детерминированное планирование inspection/report/normative/calculation и обязательного FINAL AUDIT, сбор результатов, итоговый статус | Полный воспроизводимый инженерный кейс с проверенными исходниками |
| Runtime | Общая граница handlers и отдельный Codex app-server адаптер с последовательными ролями | Локальное исполнение ролей через бесплатную модель; реальный вызов и Windows transport не проверены |
| Локальный кабинет | Worker подготавливает CORE_PLAN, проверяет SHA оригиналов, сохраняет план и source-review снимок | Исполнение профильных ролей и контроль их результатов в кабинете |
| Document Intelligence | Нормализация, source binding, кандидаты и проверки происхождения | Полнота всего документа и инженерная достоверность фактов; source review не даёт acceptance |
| Нормативная проверка | Цепочка document/edition/scope/clause/requirement/condition/comparison/conclusion, READY_FOR_EXPERT_VERIFICATION | Подтверждение редакции, применимости, пункта и результата специалистом; наличие заполненных полей не доказывает норму |
| Расчёты ЛИРА/SCAD | Комплект ролей исходных артефактов и формат SHA, READY_FOR_SEMANTIC_REVIEW | Проверка содержимого, соответствия реальных байтов SHA, семантики модели и solver-run |
| Принятие | Внешний acceptance gate обязателен; доменные proof IDs и покрытие FINAL AUDIT | Подтверждение доказательств и предметных проверок в реальном полном маршруте; облако в этом шаге не проверялось |

Вывод: ядро уже является работающим слоем планирования и проверки контрактов.
Оно пока не является завершённой автономной инженерной экспертизой. В локальном
кабинете роли остаются NOT_RUN, результаты источников UNVERIFIED,
acceptance=false и FINAL AUDIT NOT_RUN.

## Подтверждённые проблемы и исправления

1. Неизвестный status и строка вместо массива evidence_ids могли пройти до
   ACCEPTED при положительном внешнем gate. Добавлена строгая проверка AgentResult,
   AgentStatus, массивов ID, domain basis, findings и message.
2. Итоговый статус доверял ранее собранному mutable CoreState. Теперь проверяются
   канонический план, принадлежность результатов задаче/агенту, дубликаты и
   контракты; неверное состояние даёт BLOCK до вызова gate. Collect проверяет
   весь предложенный batch до изменения состояния.
3. При сохранённом ID можно было заменить ТЗ/материалы, перестроить план и оставить
   старые результаты. Независимое ревью воспроизвело ACCEPTED. Состояние теперь
   привязано к исходным значениям ID, ТЗ, полей материалов и requested_checks;
   изменение требует нового состояния и выполнения. Metadata пока информационна
   и не управляет исполнением.
4. Принимающий FINAL AUDIT мог быть записан раньше профильных результатов.
   Теперь такой порядок отклоняется; FINAL AUDIT должен следовать всем
   специалистам. Точное покрытие и внешнее принятие по-прежнему обязательны.
5. Codex prompt не содержал управляющего ТЗ и использовал буквальные backslash-n
   вместо переносов. Теперь ТЗ/материалы передаются как JSON task data отдельно
   от доверенного skill; форматирование исправлено.
6. Исключение последней роли не попадало в prior_results FINAL AUDIT.
   Runtime теперь сохраняет ошибки и недопустимые ответы как явные ERROR,
   обновляя контекст после каждого специалиста.

Материалы теперь требуют MaterialRef с непустыми уникальными ID, kind и name.
Три старых тестовых fixture передавали простую строку вместо MaterialRef;
исправлены данные fixture, а не ослаблена проверка. Supabase runtime, SQL и
облачные настройки не менялись.

## Проверки и границы

Новые регрессионные тесты сначала воспроизвели нарушения и затем прошли после
исправлений. Тесты Codex используют подмену внешнего client, а не живую модель.
**270 Python-тестов PASS, 4 Node-теста PASS, HTTP/DOM smoke PASS**, compileall и
diff-check PASS. Независимое ревью выявило перенос старых результатов на
изменённый объём проверки; после исправления 12 integrity-тестов PASS, включая
смену ТЗ и материалов. Повторное ревью не нашло оставшихся Critical/Important.
Также reviewer проверил изменение списка материалов на месте: результат BLOCK.
Первый полный прогон показал три ошибки старых MaterialRef fixture; после
исправления fixture и окончательной привязки исходной задачи весь набор прошёл.

Привязка CoreState защищает от некорректного изменения состояния в обычном
маршруте, но не от произвольного Python-кода с доступом к приватным полям.
Список proof IDs не проверяет фактическое содержание доказательств: это
обязанность auditable внешнего gate. Реальный браузер/CSP, Windows, Ollama/Codex
inference и принятие инженерного объекта не выполнялись. PDF V4 не менялся и
не перепроверялся: прежние 523 UNCERTAINTY / 11 BLOCK сохраняются.

Следующий этап — профильное исполнение CORE в локальном worker через имеющийся
model gateway с явным статусом каждого специалиста, ошибками, границами
исходников и сохранением результатов. Свободный ответ модели не становится
доказательством или инженерным принятием. Затем маршрут Drive; Windows последним.

# Выборочная адаптация ECC для ENGINEER OS

Используем идеи ECC для проверки изменений, эталонных проверок извлечения и
передачи состояния работы. Проверяющий скрипт написан для существующего формата
`local_docling_smoke.py`, использует только стандартную библиотеку Python и
не требует установки ECC, MCP, моделей или платных API.

## Сравнение сохранённого извлечения с эталоном

`scripts/evaluate_docling_extraction.py` читает два JSON: эталон и извлечение.
Он сверяет идентификаторы проекта/документа, SHA256 источника, диапазон страниц,
привязки блоков к страницам, обязательные фрагменты текста и строки таблиц.
Блок с привязкой к нескольким страницам даёт BLOCK: его текст нельзя
использовать для подтверждения содержимого конкретной страницы.
Один эталон охватывает 1–10 страниц, как существующий bounded smoke script.
Для строк таблиц учитывается количество повторений. Нормализуются только
пробельные символы; значения, единицы и порядок столбцов сохраняют значение.

Эталон должен содержать проверки для каждой страницы диапазона и заполненные
`review.reviewer`, `review.reviewed_at` (ISO 8601 с часовым поясом),
`review.source_ref`. Эти поля являются заявлением о выполненной сверке с
источником: скрипт не подтверждает личность рецензента или истинность заявления.
Ожидаемые значения следует брать из визуально проверенного PDF/PNG,
а не копировать из того же проверяемого JSON.

Результат PASS означает совпадение только с перечисленными ожиданиями эталона.
Он не доказывает полноту всей таблицы или документа. Отчёт всегда содержит
`acceptance_granted: false`, `evidentiary_status: NOT_EVIDENCE` и
`document_status: UNCERTAINTY`. Проверка не пишет в Supabase и не регистрирует
доказательства. SHA256 PDF заново здесь не вычисляется: сравниваются сведения
об источнике, записанные smoke-скриптом после хеширования PDF.

Отчёт содержит время проверки, commit кода, SHA256 обоих входных JSON,
результаты отдельных проверок и ограничения. Неверный вход, потерянная привязка
к странице, несовпадение содержимого или невозможность сохранить отчёт дают
BLOCK и код возврата 2. Успешная проверка возвращает 0. Файлы входных данных
не изменяются; путь отчёта не может совпадать с ними.

### Windows: пример для одной страницы V4

Из корня checkout, где уже находятся скрипты, выполните:

```powershell
Copy-Item .\docs\templates\docling-baseline.template.json .\.engineer-os\baseline-page-15.json
```

Шаблон содержит идентификаторы V4 и страницу 15, но `review: null` и пустые
ожидания: он намеренно не проходит проверку. Откройте исходную страницу и
заполните review и хотя бы одно ожидание. Если нужное извлечение отсутствует,
сначала выполните существующий bounded smoke test; этот инструмент PDF не парсит.

`required_text` проверяет фрагмент внутри одного блока на указанной странице.
`required_table_rows` содержит точные строки вида
`название столбца: значение | название столбца: значение`, как их записывает
адаптер. Для другого диапазона измените границы и добавьте ожидания каждой
страницы. Сверяйте названия, значения и единицы с PDF независимо от извлечения.

```powershell
.\.venv\Scripts\python.exe .\scripts\evaluate_docling_extraction.py .\.engineer-os\baseline-page-15.json .\.engineer-os\v4-docling-check\pages-0015-0015.json --output .\.engineer-os\page-15-regression.json
```

Используйте свой фактический путь к окружению и сохранённому JSON. Ожидания
для реального V4 в эту поставку не включены: исходная страница здесь не сверялась.
Тесты инструмента используют явно синтетический документ.

## Checkpoint для следующего чата или агента

Скопируйте `docs/templates/work-checkpoint.md` в каталог результатов кейса и
заполните подтверждённые действия, диапазоны страниц, пути и хеши артефактов,
версии окружения, блокировки и следующий шаг. Так другой чат сможет проверить
результаты и продолжить обработку отдельных страниц. Checkpoint хранит контекст
с пометкой NOT_EVIDENCE; правила `docs/architecture/memory-trust-boundary.md`
сохраняются. Автоматическая память ECC не подключается.

## Проверка изменений перед PR

Запускайте из корня проекта и сохраняйте реальные результаты в checkpoint:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py" -v
node --check app.js
.\.venv\Scripts\python.exe -m compileall -q engineering runtime e2e scripts
git diff --check
git diff --stat
```

Успех unit-тестов не заменяет реальный прогон Docling, миграционные проверки
Supabase или инженерный FINAL AUDIT. Отдельно записывайте NOT_RUN для этих
проверок, если их не выполняли. Вносите изменения в рабочей ветке; merge в main
требует прямого разрешения пользователя.

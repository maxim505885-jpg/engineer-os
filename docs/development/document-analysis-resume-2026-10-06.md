# Пункт 3 — продолжение анализа больших документов

При ошибке parser/модели или остановке доступны сохранённые страницы и черновики. Кнопка **«Продолжить анализ»** ставит в очередь то же задание. Готовые части с совпадающей идентичностью и контекстом используются повторно; незавершённые и неудачные части выполняются заново. Новое сообщение пользователя и новая задача не создаются. После успешного завершения появляется один ответ.

## Идентичность и границы

- SHA256 оригиналов проверяется до подготовки, до/после вызова модели и при продолжении; чужая сессия и активная задача блокируют продолжение.
- Сохраняются task/session/prompt/checks, имена и hashes источников, snapshot кандидатов/проверок, код pipeline/инструкций, версии parser и пакетов, лимиты. Для Docling записываются hashes локальных файлов моделей, настройки таблиц и языков. Это не проверка качества OCR.
- Ollama `/api/tags` даёт digest модели, `/api/show` — hash parameters/template/system/model_info. Provider/origin/model/thinking/temperature/timeout входят в идентичность. API key и полный ответ show не сохраняются. Идентичность проверяется при подготовке и по границам вызова; сервер должен быть локальным.
- Если immutable identity недоступна, первоначальный анализ возможен, но повторное использование после перезапуска запрещено. Open WebUI сейчас не предоставляет нужной идентичности через этот адаптер. Старые checkpoints без новых hashes требуют нового задания, сохранённые журналы остаются доступными.
- CHAT использует сохранённый начальный контекст. CORE part key зависит также от исходов предыдущих ролей. Изменившийся исход предыдущей роли делает её зависимые черновики непригодными для повторного использования: они пересчитываются, даже если прежний вызов завершился. Изменение источников, кандидатов, skills или конфигурации требует нового задания.
- Completed receipt содержит hash ответа, part key, зависимости сводки, refs страниц и точных текстовых сегментов. Неподтверждённый/повреждённый receipt не принимается. Повторный вызов не превращает черновик в доказательство.

## Бюджеты и остановка

Extraction: максимум 5000 страниц, 20000 символов страницы, 1000 blocks, 2000000 сохранённых символов. Модель: source part 6000 символов, aggregate source limit 2000000; 2048 попыток и 86400 секунд измеренного времени попыток на задание. Проверка временного бюджета выполняется **между** вызовами; отдельный LocalModel timeout остаётся 180 секунд. Это не жёсткое ограничение общего wall time задания: извлечение, метаданные и ожидание очереди учитываются отдельно.

Начало вызова записывается как RUNNING до inference, окончание — COMPLETED/FAILED в той же записи. При аварийном завершении RUNNING никогда не используется как ответ. Для бюджета такая попытка консервативно учитывается как 180 секунд; `model_elapsed_estimated=true`, число прерванных попыток явно записано. Это оценка, не измерение фактической длительности прерванного вызова. Перезапуск не сбрасывает calls/time budgets. Исчерпанный extraction budget переносится в parent и запрещает создание нового child через resume.

Interrupted extraction продолжает тот же child. Повторяются только страницы execution=FAILED или не обработанные; completed BLOCK/NO_NATIVE_TEXT не исчезает. Failed parser page не отправляется модели как будто документ прочитан. Сохранённый BLOCK роли остаётся BLOCK также при недоступной идентичности до replay. Все результаты сохраняют acceptance=false и FINAL AUDIT NOT_RUN.

## Потери сводок

При объединении пары черновиков передаётся до 4000 символов каждого. `summary_input_clipped` и `summary_omitted_chars` сообщают точный объём обрезания на всех уровнях/ролях; полные тексты доступны в журнале. Даже без механического обрезания смысловая сохранность не проверена. `all_batches_completed` означает завершённые source/summary calls, не полноту документа и не инженерное принятие. Page clipping дополнительно устанавливает `text_omitted`.

Контрольный четырёхстраничный fixture образует 3 source parts и 2 summaries. Ошибка второй части: 2 попытки до остановки; после продолжения ещё 4 вызова; готовая первая часть использована повторно, суммарно 6 попыток и 6 receipts. Контрольные ответы длиной 4517 символов: сводка обрезала 2068 символов; 5 полных drafts сохранили TAIL_MARKER, ни один summary input его не получил. Это воспроизводимый пример **реальной механической потери при сжатии**, а не замер качества Qwen. Metadata: `docs/qa/2026-10-06-stage3-resume.json`; искусственная задержка 0,01с/вызов, controlled in-process transport, не реальная Ollama/OCR скорость.

## Проверки и исполнение

- Initial RED: отсутствующий resume, скрытое clipping, неработающий call budget — 6 ожидаемых падений, затем GREEN.
- Additional RED→GREEN: journal перед аварией и terminal FAILED неполного CORE; final-audit skill и evidence identity guards.
- Независимый read-only whole-branch review обнаружил два Important: BLOCK downgrade до replay и reset child extraction budget. Оба воспроизведены отдельными RED tests и исправлены одним проходом; повторный review не запускался.
- Полный финальный набор: 362 Python tests, 4 Node tests, compileall/JS syntax/diff checks PASS.
- Настоящий localhost HTTP + LocalModel + Store + Worker: token/session/digest/repeated-resume guards; изменённый digest отвергнут; completed input не вызван второй раз. Synthetic HTTP model protocol, не Qwen.
- Actual launcher/worker + jsdom: ошибка второй части → перезагрузка UI → кнопка resume → тот же job SUCCEEDED, одна user message, cached call не повторён; также existing Drive scenario PASS. jsdom не является визуальным browser/Windows тестом.

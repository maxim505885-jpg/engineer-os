# Профильный анализ CORE в локальном кабинете

## Назначение

CORE_RUN выполняет предварительный анализ по управляющему ТЗ через существующий
LocalModel/OpenAI-compatible gateway. Это продолжение локального сценария
чат → файлы → очередь → worker → сохранённые результаты. Обязательное облако,
платный API и новый runtime не добавлены.

В интерфейсе выбрать «Профильный анализ по ТЗ», отметить проверки, выбрать
оригиналы и отправить ТЗ. Доступны обследование, отчёт, нормы и расчёты. По
умолчанию отчёт и нормы. EngineerCore добавляет последнюю роль сверки результатов.
Режим «План проверки по ТЗ» по-прежнему работает без вызова модели.

## Выполнение и сохранение

1. Подготовить существующий CORE_PLAN: принадлежность файлов диалогу, размер и
   SHA256 оригиналов, материалы и source-review снимок.
2. Сформировать план через EngineerCore и непроверенный контекст выбранных
   исходников/кандидатов. Сохранить точные переданные фрагменты и review-event ID.
3. Последовательно вызвать выбранные роли через LocalModel.chat с доверенным
   skill и более строгими границами локального режима в system message. ТЗ,
   исходники и прежние ответы находятся в отдельном user JSON как данные.
4. Перед и после каждого вызова перепроверить размер и hash всех оригиналов.
   Изменение исходника останавливает задачу; ответ этого вызова не сохраняется
   как завершённый анализ. Более ранние checkpoint остаются доступными.
5. Проверить строгий JSON, создать типизированный AgentResult, собрать его через
   EngineerCore и сохранить checkpoint после роли. Предварительная сверка
   получает статусы всех прежних ролей, включая ошибки.
6. Сохранить итоговую сводку в сообщениях диалога и полный результат в задаче.

Формат draft: только `status`, `summary`, `observations`, `limitations`.
Статус только UNCERTAINTY/BLOCK. Наблюдения имеют `text` и `source_ids`; IDs должны
принадлежать переданным оригиналам/кандидатам. Пустые наблюдения допустимы:
замечания не создаются ради заполнения. ERROR означает ошибку выполнения или
контракта ответа, а не доказанную инженерную ошибку объекта.

В core_run.results сохраняются execution NOT_RUN/RUNNING/COMPLETED/FAILED/
INTERRUPTED, статус, резюме, наблюдения и ограничения каждой роли. Сбой модели,
инструкции или формата — явный FAILED/ERROR; остальные роли продолжаются.
Информация исключений не переносится в ответ или следующий prompt. Изменение
оригинала является фатальным для всей задачи. Остановка worker не вызывает
следующие роли; уже завершённые draft остаются. При перезапуске прежний RUNNING
job становится FAILED, checkpoint сохраняется; автоматического повторения нет.

SUCCEEDED означает, что цикл обработки закончился и результат сохранён, а не
что все роли успешно выполнились или объект принят. Отдельный core_run.status
показывает итог ядра, включая ERROR/BLOCK. В UI результат — инертный текст.

## Лимиты и границы доверия

- До 20 выбранных файлов; до 4000 символов текста каждого и 12000 суммарно.
  Исходные preview/extraction ограничения и UNAVAILABLE раскрываются.
- Кандидатный контекст до 6000 символов JSON; quote/statement до 500 каждый.
  Усечение поля/списка помечается, candidate-ID не становится Evidence-ID.
- Подробности прежних результатов до 10000 символов JSON; статусы всех прежних
  ролей передаются отдельно, без скрытого пропуска ошибок.
- Ответ до 20000 символов; summary до 2000, до 12 наблюдений по 1500 символов,
  до 20 source_refs на наблюдение, до 12 ограничений по 500. Duplicate JSON keys,
  посторонние поля, неизвестные источники и принимающие статусы отклоняются.

Каждый результат PRELIMINARY_ANALYSIS, `evidence_ids=[]`, acceptance=false.
Модель не вызывает solver/браузер, не проверяет редакции нормативов и не получает
внешний acceptance gate. Последняя модельная роль является предварительной
сверкой: формальный FINAL AUDIT остаётся NOT_RUN. Ссылки на существующие файлы
проверяют принадлежность контексту, а не достоверность утверждений.

## Проверка

Проверки охватывают последовательность ролей и ТЗ, историю/restart, ложное
принятие, неизвестные ссылки, ошибки модели/JSON/skill, исходник до/во время
вызова, прерывание, размер контекста, чужой диалог и actual loopback HTTP.
DOM-сценарий проверяет режим, выбранные роли, три последовательных model request,
инертную разметку и восстановление после перезагрузки. Окончательные результаты
этого шага записаны в журнале проверки локального приложения.

Все model ответы в проверках синтетические. Живая qwen3, Windows, настоящий
browser/layout/CSP и полный принятый инженерный кейс не проверены. PDF V4 в этом
шаге не менялся и не перепроверялся. Следующий этап — пользовательский Drive
маршрут и усиление проверки извлечения/доменных данных перед принятием; Windows
и живая модель — в последнюю очередь по указанию пользователя.

# Source-bound normative catalog

`load_rule_catalog(path: Path) -> RuleRegistry` читает неизменяемый снимок JSON.
Верхние поля: `format_version: 1`, `registry_version`, `rules` (1–1000).
Каждое правило содержит все поля `Rule`, дополнительно `source_path` относительно
каталога. Источник — полный UTF-8 TXT/MD; абсолютные пути, выход из каталога,
неизвестные поля, повторные JSON keys/версии, NaN и неподдержанные единицы
отклоняются. Ограничения: JSON 2 MiB, один источник 50 MiB, всего 100 MiB.

Правило содержит document, edition, scope, clause, requirement, точный
уникальный `clause_text`, `source_locator`, SHA-256 полных исходных байтов,
rule_id/version, effective_from/until, operator/limit/limit_unit и явный
список accepted_data_classes. Предел с единицей должен встречаться в точном
требовании; PROJECT не заменяет MEASURED/TESTED, когда правило их требует.
Все поля, включая допустимые классы и текст пункта, входят в `rule_digest`.

Полный текст и источник необходимы, но не доказывают юридическую актуальность,
применимость или правильное толкование. PDF/OCR equivalence этим loader не
квалифицированы. В репозитории нет вымышленных или заранее принятых пунктов норм.

## Применение в существующем приложении

Через форму «Технические сведения → расширенный JSON-пакет» или существующий
POST domain-packets нормативный пакет может передать дополнительное поле:

```json
{
  "catalog_rule": {
    "registry_version": "VERSION",
    "rule": "Полный объект Rule из dataclasses.asdict; accepted_data_classes — JSON array",
    "rule_sha256": "rule_digest выбранного правила",
    "assessment_date": "YYYY-MM-DD"
  }
}
```

Это описание формы поля, а не готовый нормативный пример. Остальные поля
NORMATIVE packet сохраняются. Нормативный кандидат обязан ссылаться на полный
TXT/MD источник с тем же SHA и содержать точную цитату пункта. Сервер повторно
проверяет исходные байты, правило, дату, цепочку, оператор, предел/единицы и
классы всех фактических кандидатов. Пути из клиентского JSON не исполняются.
Правило сохраняется в immutable packet; при последующем отчёте binding
проверяется вновь. Изменённый источник или digest закрывает этот путь.

Старые пакеты совместимы. Полноценная предметная authority/reviewer приёмка и
квалификация реальных нормативных источников ещё не завершены.
Арифметика и source match не дают ACCEPTED/FINAL_AUDIT.


## Обычная форма выбора каталога

В разделе «Нормы и расчётные исходники» доступен выбор JSON-каталога из файлов
проекта и явный выбор полных TXT/MD источников. Если имена повторяются, нужно
выбрать конкретный файл по SHA. Прикладной маршрут поддерживает плоские имена
source_path; библиотечный loader по-прежнему поддерживает вложенные каталоги.

POST `/api/sessions/{id}/normative-catalog` принимает ровно `catalog_file_id`
и `source_file_ids`. Требуются существующий локальный токен и источники того же
проекта. JSON ограничен 2 MiB, источник 50 MiB, сумма выбранных используемых
источников 100 MiB; проверки хешей повторяются после чтения. Используется общий
ограничитель одновременных просмотров. Пути из JSON не открываются на сервере.

Просмотр возвращает registry_version, rule/digest, точный limit_fragment и
source file ID/SHA; ничего не сохраняет как нормативный пакет. В форме видны
цитата пункта, редакция, область, заявленный период и классы допустимых данных;
можно скачать полный источник. Автозаполнение сохраняет исходные пробелы и
переносы. Отдельно выбираются фактическая цитата и дата оцениваемой работы.
Кандидат нормативного пункта должен уже существовать с точной цитатой; он не
создаётся и не принимается автоматически.

При сохранении существующий binding повторно проверяет полный источник,
цепочку, digest, дату, единицы и классы фактических данных. Смена проекта
очищает выбор, включая отложенные ответы предыдущего проекта. Сам каталог
не подтверждает актуальность редакции, полномочия проверяющего или ACCEPTED.

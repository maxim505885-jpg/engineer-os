# ЛИРА-САПР и SCAD Office: инструменты и репозитории, 11.10.2026

Статус: исследование, не возобновление расчётного этапа. Пользовательское «scada» трактуется по контексту как SCAD Office (строительные конструкции). Промышленная SCADA, OpenSCAD и Ansys SCADE не являются подходящими заменами. Расчёты, запуск экспортёра R4 и запрос новых RES-файлов этим шагом не выполнялись.

## Основа интеграции

### ЛИРА-САПР 2024

Основной путь — собственный Windows экспортёр ENGINEER OS и документированный API установленной версии. PR101 (https://github.com/maxim505885-jpg/engineer-os/pull/101) подтверждён через GitHub как MERGED: head4410878aef76d48495398086f40e822c4bbe7349, mergef8746896d9731011fc0cf65ca6b6ee58841e6f40. Это чтение native input-table ZIP, не полный расчёт/RES.

PR102 (https://github.com/maxim505885-jpg/engineer-os/pull/102) по свежему GitHub остаётся OPEN/DRAFT, merged=false, headb623bc3abd58adbf46432fbc4e3adb96d647235c. Предварительный merge_commit_sha API не означает merge. Экспортёр R4 не объединён; реальный результат и reader resultZIP остаются открытыми по последнему подтверждённому состоянию. Расчётный этап отложен решением пользователя 09.10.2026.

Официальные возможности 2024: https://lira.land/lira/release-notes/2024/components-of-bim-technology — развитие API создания модели/доступа к результатам и таблиц ввода. Общая страница https://lira.land/lira/release-notes/api-and-input-tables содержит также версии2025/2026: не переносить их API/таблицы КЭ57/грунта автоматически на установленную2024. ЛИРА10 и ЛИРА-САПР — разные продукты; одноимённые API не считать совместимыми.

### SCAD Office

Найден первичный официальный документ: https://scadsoft.com/download/SCADAPI.pdf — «SCAD Office. Библиотека SCAD++ API»,2025,83страницы. Он описывает чтение/создание/корректировку моделей и анализ сохранённых результатов: узлы, элементы, жёсткости, связи, нагрузки, сочетания, перемещения, реакции, усилия/напряжения, РСУ/РСП, армирование.

Документ описывает C-интерфейс и API/Include/ScadAPIX.hxx, API/Lib/64, API/Demo; SCADAPIX.dll и vendor dependencies из установки SCAD. Будущий адаптер: небольшой x64 C/C++ exporter по заголовкам именно установленной версии; возможен Python ctypes только после проверки ABI/структур/calling convention. Нельзя считать SCAD COM-объектом только по аналогии с ЛИРА. Установленная версия и право использования SCAD у пользователя в этом шаге не подтверждены. Vendor DLL не объявляются открытыми/бесплатно распространяемыми. Не вводить обязательную покупку SCAD.

На чтении обязательно проверять units, нумерацию, коды возврата/ApiGetLastError, состав результатов и соответствие модели. Одно имя nativeфайла не заменяет исходные данные и каталог результатов.

## Что понадобится после нового разрешения на расчётный этап

1. ЛИРА: продолжить PR102 и resultZIP reader; подтвердить реальное сохранённое RES чтение, полноту/ошибки/разреженные ID и доступность результатов именно2024.
2. SCAD: по официальной документации и заголовкам установленной версии сделать read-only exporter на отдельной копии; использовать прежнюю границу SCAD_TEXT_ARCHIVE/vendor_adapters вместо новой архитектуры.
3. Обоим маршрутам: доказанная связь originalSHA→model snapshot→completed solver run→result; version/API/units/ID mapping; нагрузки/РСУ/РСН/материалы/сечения/связи/жёсткости; явные отсутствующие данные и сообщения solver. Графики/цветаDXF не заменяют числовые усилия/перемещения.
4. Сопоставить snapshot/results с vendorтаблицами и простыми контрольными схемами, затем с фактической конструкцией. Новый solver не обязателен; никаких обязательныхплатныхAPI.
5. Контроль версий и лицензий перед копированием/распространением; не считать публичный GitHub или бесплатный EXE разрешением копировать код.

В этом шаге сделан только отбор и уточнение технического пути. Последний runtime candidate1a765fa1766add7b5c5950a98893cd6e8099c6f8 не изменён. №13 — документы — остаётся текущим приоритетом; расчёты отложены.

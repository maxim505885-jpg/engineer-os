# Резервное копирование и восстановление ENGINEER OS
Дата: 08.10.2026. Пункт №3 выполнен для локального хранилища.

## Пользовательский путь без команд разработчика
1. Остановить кабинет через `Stop_ENGINEER_OS.cmd` (на другой платформе закрыть его консоль). Сначала дождаться завершения нужных задач.
2. Двойным щелчком открыть `Recover_ENGINEER_OS.cmd`. Он открывает браузерный режим обслуживания без модели и очереди; может использовать уже подготовленную .venv или установленный Python3.12+. В работающем кабинете ссылка «Резервные копии и восстановление» объясняет этот переход и оставляет операции отключёнными.
3. Указать полный путь к новому ZIP вне каталога данных и нажать «Создать копию». «Проверить архив» проверяет уже существующий ZIP. Путь можно скопировать из Проводника; встроенный файловый диалог пока не предусмотрен.
4. Для восстановления указать доверенный архив и НОВЫЙ отсутствующий каталог; нажать «Восстановить в новый каталог». Существующий каталог не заменяется.
5. Нажать «Выбрать этот каталог», закрыть режим обслуживания и открыть `Start_ENGINEER_OS.cmd`. Выбор хранится в `.engineer-os/active-data-dir.txt`; обычный launcher читает его автоматически. Явный `--data-dir` имеет приоритет. Для отката выбрать прежний существующий каталог в этой же форме.

Это программный маршрут №4, проверенный HTTP/DOM и Chromium на Linux. Сам двойной щелчок CMD/PowerShell и нативные Unicode-пути Windows проверяются в №16. Архивы не зашифрованы; восстановление не подтверждает инженерное содержание. Модель и внешние приложения подключаются отдельно.

## Техническое использование
Остановить приложение. Команды выполнять из каталога проекта:
```sh
python scripts/local_data.py backup --data-dir .engineer-os/local-app --out backups/project.zip
python scripts/local_data.py verify backups/project.zip
python scripts/local_data.py restore backups/project.zip --data-dir .engineer-os/restored
python scripts/run_local_app.py --data-dir .engineer-os/restored
```
Восстановление требует НОВОГО отсутствующего каталога. Рабочие данные не заменяются. Для отката запустить прежний каталог, предварительно остановив приложение. Использовать доверенную копию: SHA256 проверяет целостность, а не личность создателя архива.

## Состав и гарантии
SQLite backup API сохраняет все таблицы, историю, задачи, оригиналы, проверки и аудиты. Копируются управляемые originals/files и derived, локальный ключ engineering-verification.key при наличии и разрешённые настройки модели/провайдера/URL/thinking. API-ключи и OAuth-секреты из окружения не копируются; при необходимости их подключают отдельно. Архив содержит личные данные и issuer key, хранить его как приватную копию; архив не зашифрован.

DataLock исключает штатный запуск приложения во время операции. Архив сначала создаётся и полностью проверяется во временном каталоге, затем публикуется без перезаписи. Проверяются SHA256, размеры, SQLite integrity/foreign keys, идентичность оригиналов и полный перечень. Ошибки не публикуют частичную копию.

Restore проверяет инвентарь, запрещает обход каталогов, ссылки, дубликаты и небезопасные имена, ограничивает распаковку 10 GiB/100000 элементов/16 MiB manifest. Пути files в SQLite заменяются на новый корень; содержательные immutable JSON и их хеши не переписываются. SQLite handles закрываются до публикации. Новый каталог публикуется атомарно без замены даже конкурирующего пустого каталога. Реализация: Linux renameat2 и Windows rename; прочие платформы без этой операции отказывают безопасно.

Версия SQLite schema=1. Известная legacy schema0 обновляется транзакционно, предварительно создаётся проверенная эксклюзивная копия history.pre-migration-v0.sqlite3. Она должна совпадать с содержимым мигрируемой базы. Сбой копии позволяет повтор; сбой DDL откатывает изменения. Новая неизвестная версия отвергается. После аварии startup по-прежнему переводит RUNNING в FAILED; QUEUED остаются в очереди, повтор выполняется явно.

## Принятые границы
Копирование — offline после остановки приложения, а не горячая операция UI. Оно предполагает использование DataLock штатными процессами; изменение файлов посторонними программами не поддерживается, изменённые originals выявляются проверкой. Резервируются данные кабинета, не веса Ollama и не сторонние приложения. Диск нужен для архивирования, полной проверки и staging; недостаток места даёт ошибку без публикации. Кнопки копирования/проверки/восстановления и выбор активного каталога реализованы в режиме обслуживания №4. Активный владелец данных по-прежнему блокирует backup/activate; hot backup не добавлен. Реальные пределы нагрузки — №15, Windows — №16.

Проверки дополнения №4: 10 новых Python-тестов истории/recovery/HTTP; полный прогон 517 PASS; реальный Chromium: busy-owner refusal, backup/verify/restore, no-replace, байты originals, активация каталога с кириллицей и пробелами, запуск восстановленной истории без повторной работы модели.

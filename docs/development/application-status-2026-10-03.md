# ENGINEER OS — фактический этап разработки, 03.10.2026

**Фундамент реализован; интеграция MVP не завершена.** Есть инженерные контракты,
панель управления и серверные функции, но пока нет проверенного пользовательского
сценария «файл → анализ → доказательства → заключение → FINAL AUDIT».

Проверены текущий checkout, GitHub, код основных модулей, HTTP runtime,
Supabase metadata/счётчики, Railway и шесть ключевых облачных функций.
Это не аудит всех 94 функций, всех RLS-политик или пользовательской Windows.

## Свежая проверка инфраструктуры и данных

- Supabase `engineer-os`: ACTIVE_HEALTHY, 132 public таблицы с включённым RLS,
  94 ACTIVE Edge Functions, 132 применённые миграции. Наличие/ACTIVE не доказывают
  правильность кода или изоляцию доступа.
- В GitHub только 9 SQL-миграций и нет исходников этих 94 функций. Облачную
  систему пока нельзя воспроизвести из одного репозитория.
- Для текущего инженерного проекта: evidence=0; 32 требования NOT_CHECKED;
  FINAL AUDIT: 10 BLOCK, 7 UNCERTAINTY. Завершённые задачи/очереди не равны ACCEPTED.
- V4 в БД помечен processed и содержит 828337 символов, SHA256 совпадает.
  Это не подтверждение извлечения всех 534 страниц: ingestion-функция назначает
  processed по наличию переданного extracted_text, не по полноте/проверке.
- Изученный pipeline-launch-v1 требует MODEL_API_KEY, model-gateway также
  требует ключ для вызова провайдера. Локальный Python gateway допускает работу
  без ключа, но этот бесплатный маршрут ещё не соединён с облачным launcher.
- Railway: runtime-exec, runtime-test и основной сервис online; отдельный
  engineer-os-runtime offline. Второй проект со статическим сервисом online.
  Runtime-exec всё ещё привязан к fix/mandatory-evidence-gates; изменения из
  PR #25–27 и текущая новая ветка не считаются развёрнутыми. Production не изменялся.
- Runtime из `.venv-docling` отвечает HTTP 200 на health. Системный Python
  вне этого окружения возвращает DOCLING_UNAVAILABLE. Отключённые ingestion/E2E
  пути правильно возвращают 403. Реальный запуск агентов через Codex/Ollama
  в этой среде не подтверждён; Codex CLI здесь не найден.
- Найдена ошибка runtime: complete_document было true при запросе без диапазона,
  независимо от покрытия страниц/проверки. Исправлено: requested_full_document
  отдельно, complete_document=false, verification_status=UNCERTAINTY,
  acceptance_granted=false на обоих parse-маршрутах. Изменение не развёрнуто.

## PDF: закрытая часть и оставшаяся работа

Таблица 15–16 прошла ограниченную проверку семи строк и заголовка. Страница 11
снова извлекается после исправления штампа. Полная таблица 396–404 имеет отдельную
карту 91 восстановленной строки; новый verifier перепроверил 546 ячеек и 570
фрагментов по оригиналу. Штатный Docling на этих девяти страницах остаётся BLOCK.
Страница 499 извлекается, но ФС3/ФС6 ошибочно прочитаны как ФСЗ/ФСб; 500 BLOCK.
Инвентаризация всех 534 страниц: 40 без нативного текста, 193 с менее чем 250
символами, включая эти 40. OCR и ручная проверка графики ещё необходимы.
Исторические 137 BLOCK-страниц нельзя считать исправленными или свежим результатом.

## Порядок доведения MVP

1. Сохранить воспроизводимый backend: исходники/миграции и проверяемую конфигурацию.
2. Соединить локальный runtime с Ollama и существующим ядром, убрать обязательный
   платный/API-key путь из локального режима; проверить один реальный task.
3. Дать в UI чат, загрузку/Drive, историю, просмотр страниц и очередь проверки
   кандидатов. Частичный processed-текст никогда не считать полным доказательством.
4. Включить проверенные карты восстановления в пользовательский review workflow,
   затем расширить их на остальные таблицы/графику и получить отчёт полного покрытия.
5. Провести один реальный кейс по ТЗ: выбранные проверенные evidence → агенты →
   нормативная проверка → контроль → FINAL AUDIT. Расчёты/CAD — отдельные проверяемые
   этапы после этого, без заявлений о выполнении solver-run по одному наличию файла.

Ни main, ни базы данных, ни production-развёртывания этим проходом не менялись.
